# Roadmap — day3box

> **이 문서의 원칙**: 각 단계는 **검증할 가설**을 갖는다. 기능 목록이 아니라 가설 목록이다.
> 앞 단계의 성공 기준을 통과하지 못하면 **다음 단계로 넘어가지 않는다.**
> 이것이 이 프로젝트 최대 약점(오버엔지니어링)에 대한 구조적 방어다.

---

## 전체 그림

```
v0 — 개인 도구 / 단독 가치 검증        ← 현재 위치
      ↓  통과 조건: 본인 연속 3일 실사용
v1 — 사진 + 공유 산출물 / 실질적 런칭
      ↓  통과 조건: 본인 외 사용자가 이미지를 다운로드해 공유
v2 — 프라이빗 서클 / 성장·리텐션 엔진
      ↓  통과 조건: 그룹당 주간 활성 멤버 수
v3+ — 그 이후 (차트, 반복 블록, 알림 등)
```

**핵심**: **v1이 사실상의 제품 출시 시점**이다. v0는 출시가 아니다.

> ⚠️ **다만 v0를 "통과 의례"로 오해하지 말 것.**
> v0는 v1의 전 단계가 아니라 **v1의 전제 조건**이다.
> Lean Canvas R4(콜드 스타트)가 지적하듯, 서클이 없는 최초 사용자가 혼자서도 버틸
> 단독 가치가 없으면 사진과 서클을 붙여도 무너진다.
> **v0에서 "매일 열고 싶은가"가 증명되지 않으면 v1은 의미가 없다.**

---

## v0 — 개인 도구 / 단독 가치 검증

**검증할 가설**: *타임박싱 절차(brain dump → TOP3 → 배치 → 기록) 자체가 매일 쓸 만한가?*

**범위**: PRD F1~F9. 변경 없음. (`missed` → `moved` 반영만 적용)

### Task 순서

| # | Task | 산출물 |
|---|------|--------|
| 1 | 셋업 | Next + TS + Supabase 연결, 매직링크 로그인 동작 |
| 2 | Brain dump (F1) | 좌측 패널 task 추가/삭제, DB 저장·로드 |
| 3 | TOP 3 + 소요시간 (F2) | 승격/해제, `est_min` 입력, **교체 UX**(PRD 7.1) |
| 4 | 정적 그리드 (F3) | 06:00–24:00 세로축, 현재 시각 자동 스크롤 |
| 5 | 블록 배치 (F4) | task 클릭 → 다음 빈 슬롯 자동 배치, 소요시간=높이 |
| 6 | 이동/리사이즈 (F5) | 드래그 이동, 리사이즈, 15분 스냅, 겹침 방지 |
| 7 | 상태 토글 (F6) | planned / done / partial / **moved** |
| 8 | 날짜 이동 (F7) | 어제/오늘/내일, task·block 함께 로드 |
| 9 | 배포 | Vercel 배포, 실사용 시작 |

### 성공 기준
- **본인 연속 3일 실사용** (아침 계획 + 저녁 기록)
- 통과하지 못하면 **v1으로 넘어가지 않고 v0를 고친다.**

### v0에서 하지 않는 것
사진 · 이미지 다운로드 · 서클 · 모바일 앱 · 차트 · 반복 블록 · 알림.
단, 그리드 컴포넌트를 만들 때 "나중에 이미지로 캡처될 구조"임은 염두에 둔다(PRD 5장). **코드를 미리 작성하지는 않는다.**

## v1 — 사진 + 공유 산출물 / 실질적 런칭

**검증할 가설**: *사람들이 매일 사진을 찍어 넣는 마찰을 감수하는가?* (Lean Canvas **R3**)

이것이 제품의 본체다. v0가 데이터 입력 UI였다면, v1은 그 데이터가 **보고 싶은 산출물**이 되는 단계다.

### 범위

1. **사진 블록 삽입** — 실행한 블록 자리에 사진을 넣는다.
2. **플래너 이미지 생성·다운로드** — 하루 단위 그리드 이미지, 주간 모아보기.
3. **모바일 대응** — 사진 촬영의 전제 조건.

### 모바일을 어떻게 할 것인가 (v1 착수 시점에 결정)

v0 완료 시점에 실사용 데이터를 갖고 판단한다. 지금 결정하지 않는다.

- **경로 A — 반응형 웹 + 카메라 입력**: `<input type="file" capture>` 로 모바일 브라우저에서 촬영. 가장 빠르고 코드베이스가 하나다.
- **경로 B — Expo/RN 앱**: 네이티브 카메라 경험. 그러나 그리드 드래그 인터랙션을 다시 만들어야 한다(PRD 5장 참조).

> **현재 기울어진 방향은 A다.** 사진 입력 마찰(R3)을 검증하는 것이 목적인데, 앱 개발이라는 큰 비용을 먼저 치르고 검증하는 것은 순서가 거꾸로다. A로 검증하고, 마찰이 앱으로만 해결된다는 근거가 나오면 B로 간다.
> *(이것은 현재 판단이며 v1 착수 시 재검토한다.)*

### 이 단계에서 반드시 함께 결정할 것
- **이미지 압축·리사이즈 정책** — 사진 저장은 유일한 비선형 비용이다(Lean Canvas ⑦). 원본 저장은 하지 않는다.
- **이미지 렌더링 방식** — 클라이언트 캡처 vs 서버 렌더링.
- **설계 원칙 준수**: 결과물은 **성취를 보여주되 실패를 전시하지 않는다.** `moved` 블록이 이미지에서 어떻게 보일지가 여기서 결정된다.

### 성공 기준
- **본인 외 사용자가 실제로 플래너 이미지를 다운로드해 공유**
- 지표: 플래너 이미지 다운로드/공유 횟수

## v2 — 프라이빗 서클 / 성장·리텐션 엔진

**검증할 가설**: *서클이 형성되면 리텐션이 실제로 바뀌는가?* (Lean Canvas **R2, R4**)

### 범위
1. **초대 기반 그룹** — 링크 초대, 소규모(3~5명) 전제.
2. **서로의 플래너 보기** — 서클 멤버의 하루 그리드 열람.

### 설계 시 지킬 것
- **공개 SNS가 아니라 프라이빗 서클이다.** 팔로워·좋아요·랭킹 등 공개 소셜 메커니즘을 넣지 않는다. 무너진 하루도 보여줄 수 있어야 제약이 사라진다(Lean Canvas R2).
- **그룹이 최소 획득 단위**다. 온보딩을 개인이 아니라 그룹 기준으로 설계한다.

### 성공 기준
- **그룹당 주간 활성 멤버 수** ← **북극성 지표**
- ⚠️ DAU를 북극성으로 쓰지 않는다.

## v3+ — 그 이후

**이 시점 전에는 논의하지 않는다.**

- 달성률 차트·그래프 분석
- 반복 블록(매일/매주)
- 알림·리마인더
- 하나의 task를 여러 블록으로 쪼개는 UI
- 소셜 로그인, 실시간 동기화, 태그·검색·필터, 테마
- 수익 모델 실행 (Lean Canvas ⑥ 검증 후)

---

## 단계 이동 규칙 (오버엔지니어링 방어 장치)

1. **앞 단계 성공 기준을 통과하기 전에 다음 단계 코드를 작성하지 않는다.**
2. 기능 추가 요청이 들어오면 **Lean Canvas ③ UVP와 R1**을 필터로 쓴다 — "시간 축"과 "사진" 두 축 밖의 기능인가? 그렇다면 기각하거나 v3+로 미룬다.
3. **"나중에 쓸 거니까 미리"는 금지.** 데이터 모델도 각 단계 범위만큼만 만든다.
4. 각 단계에서 **기술 선택마다 "왜 + 배제한 대안"을 기록**한다.
5. 단계를 건너뛰고 싶어지면, 그 이유가 **검증된 근거인지 조바심인지** 구분한다.
