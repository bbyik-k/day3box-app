# PRD — day3box (타임박싱 플래너)

> **이름 상태**: 프로젝트명은 **`day3box`로 확정**한다 (구 코드네임: `Threebox`).
> 도메인·상표 확정은 v0 이후로 미룬다.
> v0 성공 기준은 "3일 이상 실사용"이지 "좋은 도메인"이 아니다.

> **문서 목적**: 이 PRD는 v0(MVP)의 범위와 결정을 못 박기 위한 문서다.
> "있으면 좋을 것"을 나열하는 위시리스트가 아니라, **무엇을 지금 만들고 무엇을
> 의도적으로 뺐는지**를 명시해 오버엔지니어링을 차단하는 장치다.
> Roadmap/Lean Canvas는 별도 문서로 분리한다.

---

## 1. 개요

### 1.1 한 줄 정의
할 일을 쏟아내고(brain dump), 그중 가장 중요한 것을 골라, 시간 블록으로 배치해 하루를 계획하고 실제 달성을 기록하는 **타임박싱 플래너**.

### 1.2 문제
일반적인 todo 앱은 "할 일 목록"은 주지만 "그 일이 하루의 어느 시간을 차지하는가"를 강제하지 않는다. 그래서 계획이 비현실적으로 부풀고(24시간에 40시간치 할 일), 실제로 무엇을 해냈는지 시간 단위로 돌아볼 방법이 없다. 반대로 캘린더 앱은 시간 배치는 주지만 "머릿속을 비우고 → 우선순위를 강제로 고르는" 사고 과정을 돕지 않는다.

타임박싱은 이 문제를 하나의 절차로 푼다: **머릿속을 다 쏟아내고 → 진짜 중요한 소수를 고르고 → 각각 시간을 추정해 → 시간 위에 배치한다.** 이 절차가 계획을 현실적으로 만들고, 하루가 끝나면 "계획 대비 실제"라는 성취 기록이 남는다.

### 1.3 타임박싱 절차 (제품이 구현하는 실제 방법론)
원본 타임박싱 기법은 노트를 좌우로 나눠 다음 순서로 진행한다. 이 절차가 곧 제품의 좌→우 화면 흐름이 된다.

1. **Brain dump (좌측):** 해야 할 일을 개수 제한 없이 전부 쏟아낸다. 머릿속에 할 일을 남기지 않는 것이 목적.
2. **TOP 3 선정 (좌측):** 쏟아낸 목록 전체에서 가장 중요한 3가지를 고른다. 우선순위를 강제하는 단계.
3. **소요시간 추정 (좌측):** TOP 3 각각에 예상 소요 시간을 적는다.
4. **시간 블록 배치 (우측):** 우측의 세로 시간축에, TOP 3를 소요시간만큼의 블록으로 **먼저** 배치한다.
5. **채우기:** 남은 시간에 우선순위 낮은 할 일이나 휴식을 끼워 넣는다.

> **이 절차가 제품 정체성이다.** 좌측(1~3)을 빼고 우측(4~5)만 만들면 그것은 그냥 캘린더다. 타임박싱이 캘린더와 다른 지점은 정확히 "쏟아내고 → 고르고 → 추정한다"는 좌측 절차에 있다.

### 1.4 핵심 원칙 (제품 정체성)
- **좌→우 흐름.** 할 일은 먼저 목록으로 태어나고(좌측), 시간 위에 배치되며 블록이 된다(우측). 이 방향성이 제품의 뼈대다.
- **Calendar-first placement.** 배치 단계에서는 할 일이 시간을 갖지 않으면 계획에 들어오지 않는다.
- **우선순위 강제.** TOP 3는 "다 하겠다"는 비현실적 계획을 막는 장치다.
- **계획과 실제를 함께 본다.** 계획만 있으면 캘린더, 실제만 있으면 로그다. 타임박싱은 둘의 대조에서 가치가 나온다.
- **하루 단위가 기본.** 주/월은 하루들의 집합으로 파생된다.

### 1.5 타깃 사용자

**v0**: 개발자 본인 1인. 시간 관리와 성취 기록이 매일 필요한 1인이 매일 쓰는 도구로 운영한다. 이것이 v0 성공 기준(1.6)의 근거다. 불특정 다수 사용자 확보는 v0의 목표가 아니다.

**v1 이후 (제품이 향하는 곳)**: 국내 20~30대, 3~5명 단위로 서로 자극을 주며 지내는 그룹(스터디 메이트, 취준 동기, 운동 메이트). 이들은 계획을 세우지만 혼자서는 3일 만에 무너지고, 지켰더라도 남는 기록이 없다는 문제를 갖는다. **개인이 아니라 그룹이 최소 획득 단위**다.

> **v0와 v1의 관계 (오해 주의).**
> v0의 개인 도구 단계는 v1으로 가기 위한 통과 의례가 **아니라 v1의 전제 조건**이다.
> 서클(v2)이 리텐션 엔진이지만, 서클이 없는 최초 사용자가 **혼자서도 며칠은 버틸 단독 가치**가
> 없으면 서클을 붙여도 무너진다(Lean Canvas R4 콜드 스타트 참조).
> 따라서 v0를 대충 만들고 v1으로 넘어가려는 힘을 경계한다. v0가 실패하면 v1은 의미가 없다.

### 1.6 v0 성공 기준 (측정 가능)
- 배포되어 있고, **개발자 본인이 실제로 아침에 계획(brain dump→TOP3→배치)하고 저녁에 상태를 기록**하는 데 쓴다.
- "될 것 같다"가 아니라 **연속 3일 이상 실사용**을 최소 통과선으로 둔다.
- 이 기준을 통과하기 전에는 어떤 확장 기능(사진/차트/공유)도 시작하지 않는다.

## 2. v0 범위 (MVP)

### 2.1 포함 (In Scope)

| # | 기능 | 설명 | 완료 정의 |
|---|------|------|-----------|
| F1 | Brain dump | 좌측 패널에서 할 일을 개수 제한 없이 입력·삭제 | 항목 추가/삭제가 DB에 저장, 새로고침 후 유지 |
| F2 | TOP 3 선정 | brain dump 항목 중 3개를 TOP3로 승격, 소요시간(분) 입력 | 승격/해제, 소요시간 저장, **3개 초과 시 교체 UX 동작**(7.1) |
| F3 | 하루 타임 그리드 | 우측 세로축 시간(06:00–24:00), 눈금선 | 정적으로 그려지고 뷰가 안정적 |
| F4 | 블록 배치 | 좌측 task(주로 TOP3)를 우측 그리드로 배치. 소요시간이 블록 높이가 됨 | task→블록 배치 → DB 저장 |
| F5 | 블록 이동/리사이즈 | 배치된 블록을 드래그로 이동, 가장자리로 크기 조절 | 분 단위 스냅, 겹침 방지 동작 |
| F6 | 계획 대비 실제 상태 | 블록에 planned/done/partial/moved 상태 토글 (`missed` 아님 — 4.1 참조) | 클릭으로 상태 전환, DB 반영 |
| F7 | 날짜 이동 | 어제/오늘/내일 이동 | 날짜별 task·블록이 올바르게 로드 |
| F8 | 인증 | 이메일+비밀번호 로그인 (매직링크에서 전환 — 5장 참조) | 로그인한 유저의 데이터만 조회/수정 |
| F9 | 영속성 | Supabase Postgres 저장 | 새로고침·재로그인 후 데이터 유지 |

### 2.2 명시적 제외 (Out of Scope — v0에서 만들지 않음)

아래는 **의도적으로 뺐다.** "나중에 쓸 거니까 미리"는 이 프로젝트 최대 약점(오버엔지니어링)의 진입로다. v0 성공 기준을 통과한 뒤 착수한다.

**단, "제외"는 "안 만든다"가 아니라 "지금 안 만든다"이다.** 아래 v1 항목들은 오히려 제품의 본체에 가깝다. 우선순위를 명시해 문서가 잘못된 신호를 주지 않게 한다.

**[v1 최우선 — 제품 정체성의 핵심. v0 통과 즉시 착수]**
- 사진 촬영·블록 삽입 (콜라주) — *제품의 본체*
- 하루/주간 플래너 이미지 다운로드 — *성장 엔진*
- 프라이빗 서클(초대 기반 그룹 공유) — *리텐션 구조*
- 모바일 대응 — *사진 촬영의 전제 조건*

**[v2 이후 — 필요가 증명되면]**
- 달성률 차트·그래프 분석
- 반복 블록(매일/매주)
- 알림·리마인더
- 하나의 task를 여러 블록으로 쪼개는 UI (모델은 1:N 허용, UI만 제외)
- 소셜 로그인(구글/깃허브 등)
- 멀티 디바이스 실시간 동기화(Realtime)
- 태그·검색·필터
- 다크모드 등 테마

## 3. 사용자 시나리오 (v0)

**아침 계획 (좌→우 흐름).**
사용자가 오늘 날짜를 연다. 좌측에 오늘 해야 할 일을 떠오르는 대로 쏟아낸다(brain dump) — "이력서 수정", "면접 스터디", "운동", "장보기", "포트폴리오 리팩터"… 그다음 이 중 가장 중요한 3개를 TOP 3로 올리고 각각 소요시간을 적는다("이력서 수정 90분" 등). 이제 우측 그리드로 TOP 3를 끌어와 배치한다. 소요시간이 이미 있으니 블록 높이가 자동으로 정해진다. 겹치게 놓으려 하면 막힌다. 남는 시간에 나머지 할 일과 휴식을 끼워 넣는다.

**저녁 기록.**
하루가 끝나고 다시 연다. 완료한 블록은 done, 절반만 한 건 partial, 하지 못해 내일로 넘기는 건 moved로 표시한다. 그리드가 "계획했던 하루"와 "실제 보낸 하루"를 한눈에 보여준다.

**넘어가는 할 일.**
어제 좌측에 쏟아냈지만 배치하지 않은 할 일은 사라지지 않는다. 오늘도 좌측에서 다시 보이거나 오늘로 가져올 수 있다("오늘 못 한 걸 내일로"). — *이 흐름을 위해 데이터 모델에서 길 B(task 영속화)를 택했다.*

**돌아보기.**
어제로 이동해 어제의 그리드를 본다. 무엇을 계획했고 무엇을 해냈는지 시각적으로 남아 있다.

## 4. 데이터 모델 (v0)

v0는 **두 테이블**로 구성된다. `tasks`(무엇을 할까 — 좌측)와 `blocks`(언제 할까 — 우측). 사진·공유·팔로우 테이블은 만들지 않는다.

```
tasks                                     -- brain dump 항목. 시간 없음. "무엇을".
  id            uuid         primary key   default gen_random_uuid()
  user_id       uuid         not null      references auth.users(id)
  date          date         not null      -- 어느 날의 brain dump인가
  title         text         not null
  is_top3       boolean      not null      default false  -- TOP3로 승격됐는가
  est_min       int                        -- 예상 소요시간(분). TOP3일 때 입력
  category      text                       -- 색상/분류. 자유 문자열로 시작
  created_at    timestamptz  not null      default now()

blocks                                    -- 시간 위에 놓인 task. "언제".
  id            uuid         primary key   default gen_random_uuid()
  user_id       uuid         not null      references auth.users(id)
  task_id       uuid         not null      references tasks(id) on delete cascade
  date          date         not null      -- 배치된 날 (조회 편의를 위해 비정규화 보관)
  start_min     int          not null      -- 자정 기준 분 (09:00 = 540)
  end_min       int          not null      -- (10:30 = 630), end > start
  status        text         not null      default 'planned'
                                           -- 'planned'|'done'|'partial'|'moved'
  created_at    timestamptz  not null      default now()
```

**관계:** `tasks` 1 : N `blocks`. 하나의 task가 여러 블록으로 쪼개질 수 있으나(예: 2시간을 오전·오후로 분할), **v0에서는 이 분할 UI를 제공하지 않는다**(2.2 제외 항목). 모델만 1:N을 열어두고 UI는 사실상 1:1로 운용한다.

**제목·카테고리는 task에만 둔다(정규화).** 블록은 `task_id`로 참조하고 제목/카테고리는 task에서 읽는다. 데이터 중복이 없고, task 이름을 고치면 블록 표시도 자연히 따라온다. 이는 과한 정규화가 아니라 관계형 DB의 기본 사용이다.

**RLS(Row Level Security):** 두 테이블 모두 `user_id = auth.uid()` 인 행만 select/insert/update/delete 가능하도록 정책을 건다. 이것이 "로그인한 유저의 데이터만"을 DB 레벨에서 보장한다.

### 4.1 설계 결정과 근거

**task와 block을 분리한다 (길 B).**
brain dump는 화면 장식이 아니라 매일 반복되는 핵심 행위다. 쏟아낸 할 일이 새로고침 한 번에 날아가면 실사용에서 바로 이탈하고, 그러면 "3일 이상 실사용"이라는 v0 성공 기준 자체가 위협받는다. 또한 "배치 안 한 할 일이 날짜를 넘겨 유지된다"는 흐름은 실제 사용 패턴("오늘 못 한 걸 내일로")과 맞는다. 따라서 task 영속화는 미래를 위한 미리 만들기가 아니라 **v0가 쓸 만해지기 위한 현재 필요**다.
*(배제한 대안: 길 A — brain dump/TOP3를 화면 상태로만 두고 배치된 블록만 저장. 새로고침 시 미배치 할 일 소실로 실사용성이 떨어져 배제.)*

**상태값을 `missed`가 아니라 `moved`로 둔다.**
`missed`는 기록이 아니라 **심판**이다. 빨간 missed 블록이 늘어선 화면을 다시 열고 싶은 사람은 없고, 이는 리텐션을 직접 깎는다. 타임박싱 앱의 알려진 실패 패턴(계획이 무너지면 "계획 대비 실제"가 자책 기계가 되어 이탈)이 정확히 여기서 발생한다. `moved`(내일로 옮김)는 **같은 데이터, 다른 심리**다 — 실패가 아니라 이월이 된다. 3장 "넘어가는 할 일" 시나리오와도 의미가 일치한다.
*(설계 원칙: **결과물은 성취를 보여주되 실패를 전시하지 않는다.** 이 원칙은 v1 공유 기능까지 관통하므로, 상태 모델 단계인 지금 반영해야 v1에서 스키마를 뒤엎지 않는다.)*
*(배제한 대안: `missed` — 심리적 비용이 기록 가치보다 크다고 판단해 배제. 단순 미완을 별도로 구분할 필요가 실사용에서 확인되면 그때 추가한다.)*

**시간을 timestamp가 아닌 int(분)로 저장한다.**
타임박싱 블록의 본질은 "특정 날짜 안에서의 상대적 위치(자정으로부터 몇 분)"다. UI가 하는 일도 결국 분 → y좌표 변환이다. 정수로 두면 그리드 렌더링, 겹침 검사, 리사이즈 계산이 전부 단순 산술이 된다. timestamptz는 매 렌더마다 타임존·날짜 파싱을 끌어들여 계산을 지저분하게 만든다.
*(배제한 대안: `timestamptz` 컬럼 2개 — 타임존 처리 부담과 렌더 계산 복잡도 때문에 배제.)*

**status를 Postgres enum이 아닌 text로 시작한다.**
enum은 값 추가/변경에 `ALTER TYPE`이 필요해 초반에 족쇄가 된다. v0에서 상태값이 더 늘어날지(예: 'in_progress') 아직 확정되지 않았다. 타입 안전성은 **앱 레이어의 TS union type**으로 잡는다(`as/any` 금지 원칙과 일치). 값이 확정되면 그때 CHECK 제약이나 enum으로 조인다.
*(배제한 대안: Postgres enum — 초기 스키마 경직성 때문에 배제. 오타 방지가 필요하면 CHECK 제약은 도입 가능.)*

**겹치는 블록을 금지한다.**
순수 타임박싱 철학은 "한 시점엔 한 가지 일"이다. 겹침을 금지하면 데이터·UI 모델이 극적으로 단순해진다(한 시간대 = 최대 한 블록). 병렬 작업 표현은 잃지만, v0에서는 정의에 충실함과 구현 단순성을 택한다.
*(배제한 대안: 겹침 허용 + 레인 배치 렌더링 — 렌더 복잡도 대비 v0 가치 낮아 배제.)*

**block.date를 비정규화로 함께 둔다.**
날짜는 task에도 있지만, "그 날의 블록을 그린다"는 가장 잦은 조회를 task 조인 없이 처리하기 위해 block에도 date를 둔다. 배치 시 task.date를 복사한다. 이 소량의 비정규화는 조회 단순성과 맞바꾼 의도적 선택이다.

## 5. 기술 스택 (v0)

| 영역 | 선택 | 근거 | 배제한 대안 |
|------|------|------|-------------|
| 프레임워크 | Next.js (App Router) + TypeScript | 익숙한 스택으로 진짜 어려운 문제(그리드 인터랙션)에 집중 | — |
| 백엔드/DB | Supabase (Auth + Postgres) | BUDIT 경험 재활용, Auth·DB·RLS 일괄 제공 | 자체 백엔드(불필요한 초기 비용) |
| 인증 | 이메일+비밀번호 | 1인 도구 — 이메일 의존 제거로 개발·테스트·실사용 마찰 제로 (2026-07-28 매직링크에서 전환) | 매직링크(내장 메일 시간당 2통 제한, 템플릿 편집에 SMTP 요구, PKCE 동일 브라우저 제약) / 소셜 로그인 다중(초기 과잉, v1+ 재검토) |
| 드래그/리사이즈 | 라이브러리 없이 직접 구현 | "y축 픽셀 → 분 스냅"은 좁은 특수 문제. 범용 dnd 라이브러리는 과함. pointer 이벤트·cleanup·파생 계산 강점이 그대로 드러남 | dnd-kit 등(이 케이스에 과함) |
| 배포 | Vercel | Next와 자연스러운 통합 | — |
| 상태관리 | React 내장(useState/useReducer 등) | v0 규모에 전역 상태 라이브러리 불필요 | Redux/Zustand 등(현 규모에 과함) |

**좌측 리스트 ↔ 우측 그리드 간 드래그.**
좌측 task를 우측 그리드로 끌어와 배치하는 인터랙션은 "리스트→그리드" 이동이라 F5의 그리드 내 드래그와 성격이 다르다. v0에서는 이를 과하게 만들지 않는다. 최소 형태는 "좌측 task 클릭 → 우측에 소요시간만큼 블록 생성(빈 시간에 자동 배치 또는 클릭 지점에 배치)"이며, 정교한 drag-across는 실사용 후 필요하면 개선한다. *(이 판단은 6장 Task 순서에 반영.)*

**모바일(RN/Expo)을 v0에 넣지 않는 이유(핵심 결정).**
타임박싱의 핵심 UX는 시간 그리드 위 드래그/리사이즈다. 이 인터랙션은 웹(pointer)과 네이티브(gesture)에서 구현이 완전히 다르다. RN/Expo에 미숙한 상태로 웹+앱을 한 코드베이스에 묶으면 진짜 문제 대신 크로스플랫폼 인터랙션 차이에 에너지를 태우게 되고 양쪽 다 어중간해진다. 따라서 **웹으로 먼저 완성·운영 → 모바일이 진짜 필요해지는 순간(예: 외출 중 사진 촬영)이 명확해지면 그때 Expo 확장**한다. 이 순서 자체가 제품 진화의 자연스러운 서사다.

---


**v1 공유를 염두에 둔 설계 방향 (기능 아님, 방향 확인만).**
v1에서 그리드는 이미지로 렌더링되어 다운로드된다. v0의 그리드 컴포넌트를 만들 때, 나중에 이미지로 캡처했을 때 그럴듯하게 보일 구조인지만 염두에 둔다. 구체적으로는 (a) 블록 내부에 사진이 들어갈 여지가 있는지(블록 최소 높이), (b) 그리드 전체가 독립적으로 렌더 가능한 단위인지. **v0에서 이를 위한 코드를 미리 작성하지는 않는다.** 이것은 구현 지시가 아니라 구조 감각의 문제다.

## 6. 구현 순서 (Task 분해)

Roadmap 문서에서 더 상세히 다루되, v0 내부 순서는 다음과 같다. 각 Task는 눈에 보이는 산출물로 끝난다. **좌측(계획 도구)을 먼저 세우고 우측(그리드)으로 간다** — 제품의 좌→우 흐름과 같은 순서다.

1. **셋업** — Next + TS + Supabase 연결, 이메일 로그인까지 동작.
2. **Brain dump (F1)** — 좌측 패널에서 task 추가/삭제, DB 저장·로드.
3. **TOP 3 + 소요시간 (F2)** — task를 TOP3로 승격/해제, est_min 입력.
4. **정적 그리드 (F3)** — 우측 06:00–24:00 세로축·눈금선. 데이터 없이 뼈대.
5. **블록 배치 (F4)** — 좌측 task를 우측에 블록으로 배치(소요시간=높이), 저장.
6. **이동/리사이즈 (F5)** — 드래그 이동, 가장자리 리사이즈, 분 스냅, 겹침 방지.
7. **상태 토글 (F6)** — planned/done/partial/moved 전환.
8. **날짜 이동 (F7)** — 어제/오늘/내일. task·block 함께 로드.
9. **배포 + 실사용** — Vercel 배포 후 본인이 실제로 사용. 성공 기준(1.6) 검증.

착수 후 흔들리지 않도록 아래를 **확정**한다. 열린 질문이 아니라 결정 사항이다.

| # | 항목 | 확정 | 근거 |
|---|------|------|------|
| 1 | 그리드 시간 범위 | **06:00–24:00 고정 + 진입 시 현재 시각으로 자동 스크롤** | 범위보다 스크롤 위치가 체감 UX를 좌우 |
| 2 | 스냅 단위 | **15분** | 5분은 그리드가 촘촘해지고, 모바일 확장 시 손가락으로 잡기 어려움 |
| 3 | 카테고리(색상) | **프리셋 5색, 이름만 편집 가능** | 자유 입력은 색 관리 UI를 유발. 5색 제한은 v1 이미지 미학과도 직결 |

### 7.1 #5 상세 — 하드 제한을 택하되, 교체 UX가 조건이다

PRD 초안은 "3개 강제는 답답할 수 있으니 소프트하게"였다. 이를 **뒤집어 하드 제한으로 확정**한다.

**채택한 근거 (단 하나로 충분하다):**
TOP3 제약은 이 제품의 정체성 그 자체다(1.4 "우선순위 강제"). 소프트하게 두면 TOP3는 장식이 되고, 제품은 시간 축이 붙은 평범한 todo 리스트로 퇴화한다. 우선순위를 강제하지 않는 타임박싱은 타임박싱이 아니다.

**채택하지 않은 근거 (기록해 둔다 — 논리가 약하므로 재사용 금지):**
- ~~"이름(day3box)에 3이 들어가므로 3이 지켜져야 한다"~~ → 순서가 거꾸로다. 이름이 제품을 따라가야지 제품이 이름을 따라가면 안 된다.
- ~~"답답할 수 있어서는 제품을 평범하게 만드는 흔한 경로"~~ → 일반론으로는 맞으나, v0의 유일한 성공 기준이 **본인의 3일 연속 실사용**이다. 사용자가 한 명인 단계에서 "답답함"은 무시할 감성이 아니라 성공 지표에 직결되는 변수다.

**조건: 교체 UX 없는 단순 차단은 불가.**
4번째를 올리려 할 때 그냥 막으면 위의 "답답함" 리스크가 그대로 실현된다. 대신 **기존 TOP3 중 하나를 내리게 하는 교체 흐름**을 제공한다. 막는 것이 아니라 **선택을 강제하는 것**이며, 이것이 우선순위 강제라는 원칙의 올바른 구현이다. 이 교체 UX는 F2의 완료 정의에 포함된다.

## 8. 이 문서가 지키는 규율

- v0 범위 밖 기능은 **명시적 제외 목록(2.2)**에 넣어 "나중에"를 문서로 못 박았다.
- 모든 기술 선택에 **근거 + 배제한 대안**을 붙였다(5장, 4.1).
- 데이터 모델은 v0 범위만큼만(두 테이블). 사진·공유·팔로우 등 미래 테이블을 미리 만들지 않는다.
- task를 여러 블록으로 쪼개는 것은 모델만 허용하고 **UI는 v0에서 제외**해 범위를 좁혔다.
- 성공 기준(1.6)을 통과하기 전에는 확장을 시작하지 않는다.
