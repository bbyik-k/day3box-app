## D11. 드래그 프리뷰 — 커서를 따라오게 (최우선)

### 문제
드래그 중 항목이 커서를 따라오지 않아 **드래그가 시작됐는지조차 알 수 없다.**

Task 014 보고에는 "손잡이를 끌면 고스트가 따라오고"라고 되어 있으나, 실사용상 **리스트→그리드 구간**에서 피드백이 끊긴다. 커서가 그리드 밖(좌측 칼럼)에 있는 동안 프리뷰를 어디에 그릴지가 정의되지 않은 것으로 추정된다.

> ⚠️ **이것은 개선 항목이 아니라 미완성이다.** 그리고 D12~D15의 "헷갈린다"는 체감을 증폭시키고 있을 가능성이 높다. **반드시 먼저 처리할 것.**

### 결정 — 두 층으로 나눈다

| 층 | 역할 | 표시 위치 |
|---|---|---|
| **드래그 프리뷰** | "지금 무엇을 잡고 있는가" | 커서를 따라다님. 리스트 위든 그리드 위든 **항상** |
| **스냅 고스트** | "어느 슬롯에 놓이는가" | 그리드 안. 10분 스냅 (기존 구현) |

- 프리뷰 내용: 항목 이름 + 길이 정도. 반투명, 커서에 살짝 오프셋.
- 그리드 진입 시 **둘이 동시에 보인다.** "잡았다 → 여기 놓인다"가 끊기지 않아야 한다.
- 겹침 등으로 드롭 불가일 때는 기존 규칙(중립 실선) 유지.

### 소스 확인 필요
- 현재 고스트가 그리드 컨테이너 내부에만 렌더되는지. 그렇다면 프리뷰는 **body 레벨(portal)** 로 띄워야 커서를 따라갈 수 있다.
- 가장자리 자동 스크롤 중에도 프리뷰가 유지되는지.

## D12. 배치/미배치 구분 강화

### 문제
D9-4에서 밝기 0.72를 적용했으나 구분이 약하다. 실제 화면에서 헤더는 `1개 남음`인데 `독서`(미배치)와 `회의준비`(배치됨)가 거의 같아 보인다.

### 결정
**1단계 — 농도를 먼저 내린다. 0.5~0.55 시도.**

004에서 "비활성으로 읽히지 않는 선"이라고 경고했으나 **그 경고가 과했다.** 손잡이가 남아 있고 호버가 반응하면 비활성으로 읽히지 않는다.

**2단계 — 그래도 부족하면 보조 채널을 추가한다.**

⚠️ **우측 배지 자리는 쓰지 말 것.** D10(완료 표시)을 위해 비워둔 자리다.
→ 대신 **호버 힌트가 뜨는 가운데 영역**을 쓴다. 배치된 행에만 아주 조용한 상시 표시를 둔다. D10과 자리가 겹치지 않는다.

### 채널 배정 (재확인)
| 정보 | 채널 |
|---|---|
| TOP 3 여부 | 좌측 색 막대 + 우측 배지 |
| 배치 여부 | **밝기** (+ 필요 시 가운데 영역) |
| 완료 여부 (D10, 미착수) | **우측 표식** — 예약됨 |

## D13. 클릭 배치 → "마지막 블록 뒤"

### 문제
현재 클릭 배치는 "빈 공간 중 들어갈 수 있는 곳"을 찾는다. 시스템이 최적을 찾는 방식이라 **사용자가 결과를 예측할 수 없다.** 04:00 같은 엉뚱한 새벽 시간대에 들어가기도 한다.

### 결정
**마지막으로 배치된 블록 뒤에 붙인다.**

- 예측 가능하다는 것이 유일하고 충분한 근거다.
- 드래그가 생긴 이상 **클릭은 "대충 놓고 나중에 옮김"의 빠른 경로**로 성격이 명확해진다. 정밀 배치는 드래그가 담당한다.

**예외 — 마지막 블록 뒤에 공간이 없을 때**(예: 마지막 블록이 새벽 3시 근처)
→ **그때만 기존처럼 빈 슬롯을 탐색한다.**
→ ⚠️ 이 경우 **어디에 놓였는지 알려줄 것.** 예측이 깨지는 유일한 경우이므로, 해당 블록으로 스크롤하거나 짧게 강조한다.

## D14. 행 전체 드래그 + 제목 인라인 편집

### D14-1. 드래그 시작 영역을 행 전체로

손잡이뿐 아니라 행 어디서든 드래그 시작 가능.

**⚠️ 손잡이는 제거하지 않는다.** 드래그 가능하다는 어포던스가 사라진다. 행 전체가 되더라도 손잡이는 시각 신호로 남는다.

### D14-2. 드래그 임계값

**5px.** mousedown 후 5px 이상 이동하면 드래그, 안 움직이고 떼면 그 지점의 클릭 동작.

이것이 구글 캘린더가 쓰는 방식이며(클릭=편집 / 눌러서 이동=블록 이동), **클릭 대상과 드래그를 충돌 없이 공존시키는 표준 해법**이다.

> v1 모바일에서는 8~10px로 상향 검토. 손가락은 마우스보다 흔들린다.

### D14-3. 제목 인라인 편집 (신규 기능)

현재 제목 편집 기능이 없다. 이번에 추가한다.

**진입: 제목 클릭 (단일 클릭).**

⚠️ **더블클릭은 채택하지 않는다.** 첫 클릭이 이미 "배치"를 실행하므로, 더블클릭을 받으려면 클릭 처리를 250ms 지연시켜야 하고 그러면 배치가 굼떠진다.

**클릭 대상별 역할 분리** — 각 지점이 뜻을 하나만 갖는다.

| 대상 | 동작 |
|---|---|
| 행 어디서든 드래그(5px↑) | 시간 위에 배치 |
| **손잡이 클릭** | 마지막 블록 뒤에 배치 (D13) |
| **제목 클릭** | 제목 편집 |
| **TOP 3 배지 클릭** | TOP 3 토글 |

> D14-1의 요청은 **드래그**를 행 전체로 넓히자는 것이지 클릭 배치까지 넓히자는 것이 아니었다. 클릭 배치를 손잡이에 남겨두면 충돌이 없다.

**편집 동작**
- `Enter` 저장 / `Esc` 취소 / `blur` 저장
- ⚠️ **빈 값이면 원래 제목으로 되돌린다.** 삭제로 처리하지 말 것 — 실수로 지웠을 때 항목이 사라지면 안 된다.
- 편집 중에는 드래그 비활성화
- 입력 필드는 `+ 할 일 추가...`와 같은 스타일 사용 (새 어휘를 만들지 않는다)
- **호버 시 제목 영역에 옅은 배경이나 밑줄** — 클릭 전에 편집 가능함을 알린다. 할 일 앱들의 공통 관례다.

### D14-4. 그리드 블록에도 같은 규칙 적용

제목 편집은 리스트와 블록 **양쪽에서** 가능해야 한다. 같은 규칙이 두 곳에 적용되므로 새 어휘가 생기지 않는다.

| 대상 | 동작 |
|---|---|
| 블록 드래그(5px↑) | 블록 이동 |
| 가장자리 드래그 | 리사이즈 |
| **제목 클릭** | 제목 편집 |
| 상태 표식 클릭 | 상태 순환 |

⚠️ **블록 상세 팝오버를 만들지 말 것.** 구글 캘린더가 팝오버를 쓰는 이유는 필드가 많기 때문(시간·알림·참석자·캘린더). 우리 블록의 편집 대상은 **제목 하나**다.

**정규화 확인**: 제목은 `tasks`에만 있고 블록은 `task_id`로 참조하므로(PRD 4장), 한쪽에서 고치면 양쪽에 반영된다. **낙관 업데이트 경로가 블록 렌더링까지 갱신하는지 확인할 것.**

### 되돌릴 조건 (기록해 둘 것)
행 전체 드래그는 **업계 표준에서 살짝 벗어나는 선택**이다. Todoist·Things 등은 대부분 드래그를 손잡이에 한정하는데, 이유가 정확히 행 내부 클릭 대상과의 충돌이다.

→ 구현 후 **"제목을 고치려다 드래그가 시작된다"는 마찰이 생기면, 손잡이 한정으로 되돌리는 것이 정상 경로다.** 그것이 업계 기본값이다.

## D15. TOP 3 카드에서도 드래그 배치

TOP 3 카드에서도 손잡이/카드 드래그로 그리드에 배치 가능하게 한다.

**근거**: 현재 brain dump 리스트에서만 드래그가 되면 "왜 여긴 안 되지"가 된다. 리스트 드래그 로직을 그대로 재사용할 수 있어 비용도 낮을 것으로 추정.

**주의**: TOP 3 카드에는 이미 칩과 스테퍼가 있어 클릭 대상이 많다. **제목 영역만 편집으로 두고 칩·스테퍼는 건드리지 말 것.** 드래그 임계값(5px)이 이들과의 충돌을 막는다.

## 7. 작업 순서와 근거

```
D11 (프리뷰)  →  D12 (구분)  →  D13 (클릭 배치)  →  D14 (드래그+편집)  →  D15 (TOP3)
```

- **D11이 최우선**: 피드백 자체가 끊긴 상태다. 다른 항목의 체감 문제를 증폭시키고 있을 가능성이 높아, 먼저 고치면 D12~D15의 체감이 달라질 수 있다.
- **D12·D13**: 매일 겪는 혼동. 값 조정과 규칙 변경이라 비용이 낮다.
- **D14**: 신규 기능(제목 편집) 포함이라 가장 무겁다.
- **D15**: 일관성 확보. D14의 임계값 구현을 재사용한다.

## 8. Claude Code 판단 요청

1. **D11 — 현재 고스트의 렌더 위치 확인.** 그리드 컨테이너 내부에만 렌더된다면 커서 추종 프리뷰는 portal이 필요하다. 자동 스크롤 중 유지 여부도 함께 볼 것.
2. **D12 — 농도 값은 실물에서 조정.** 0.5부터 시작해 올려가며 판단. 기준은 **"배치된 항목을 다시 끌고 싶을 때 눈에 들어오는가"**.
3. **D14 — 임계값 구현을 리스트·블록·TOP3 카드에서 공유 가능한지.** 세 곳에 같은 로직이 들어가므로 훅이나 유틸로 한 번만 작성할 것.
4. **D14-4 — 제목 낙관 업데이트가 블록 렌더링까지 갱신하는지 확인.**
5. **미결 1번을 문서에 확정으로 승격할 것** (§6 참조).
6. **범위 이탈 감시 유지.** 블록 상세 팝오버, 제목 외 필드 편집, 새 추상화 계층이 필요해 보이면 멈추고 먼저 보고할 것.

## 9. 이 사이클 이후 — v1 판단

이번 5건은 실사용에서 나온 것이고 대부분 직전 기능의 마감이므로 정당하다. **다만 이것으로 개선 사이클을 한 번 닫는다.**

v0 성공 기준(본인 연속 3일 실사용)에 도달했거나 근접한 상태다. 도구는 이미 쓸 만하며, 여기서 계속 다듬으면 "완성도"라는 이름으로 **v1(사진)이 계속 밀린다.**

→ D11~D15 완료 후에는 새 개선 항목을 받기 전에 **3일 기록 상태를 확인하고 v1 착수 여부를 판단한다.**
