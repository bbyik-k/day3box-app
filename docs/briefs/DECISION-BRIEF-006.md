## D16. task 추가 입력 지연 — 낙관 반영 누락 (최우선)

### 문제

brain dump에서 할 일을 추가하면, 항목이 목록에 나타난 뒤에도 **입력창이 비워지는 데 약 1초가 걸린다.** 그 사이 다음 항목을 입력할 수 없다.

### 왜 최우선인가

**brain dump의 핵심 동작을 직접 막는다.** 이 패널의 목적은 "머릿속을 다 쏟아내는 것"(PRD §1.3-1)인데, 항목마다 1초씩 끊기면 생각의 흐름이 끊긴다. **우회로가 없다.**

이것은 개선이 아니라 **Task 009.5(낙관 반영 전면 확장)의 누락**으로 보인다. 색·소요시간·배치·삭제·이월은 낙관 반영으로 전환됐으나 **task 추가만 서버 왕복을 기다리고 있는 것**으로 추정된다.

### 결정

- Enter 즉시 **입력창을 비우고 목록에 낙관 추가**, 서버 저장은 뒤에서 진행
- 실패 시 롤백 + 에러 표시 (기존 낙관 스토어의 실패 처리 규칙과 동일하게)
- 연속 입력이 끊기지 않아야 한다 — **항목 5개를 쉬지 않고 타이핑해 넣는 것이 검증 시나리오**

### 소스 확인 필요

- 현재 task 추가 경로가 `DayView` 낙관 스토어(ADR-0001)를 타는지, 서버 액션 응답 후 상태를 갱신하는지.
- 입력창 초기화 시점이 응답 이후에 묶여 있는지.

## D17. 빈 구간에 들어갈 만큼만 부분 배치

### 문제

잔량 140분인 task를 60분짜리 빈 구간에 드롭하면 **거부된다.** 사용자는 "먼저 잔량을 60분으로 줄이고 → 드래그"라는 우회 절차를 밟아야 한다.

### 결정

**빈 구간에 들어가는 만큼만 배치한다.** 예: 잔량 140분 → 60분 구간에 드롭 → 60분 블록 생성, 잔량 80분.

**근거**: 타임박싱은 **가용 시간에 일을 맞춰 넣는 것**이다. 그리고 우리 모델은 이미 `est_min`(계획 총량)과 블록 길이(실제 배치)를 분리해 뒀고(ADR-0002), 분할도 지원한다. **140분 중 60분만 놓인 상태는 모델상 완전히 정상**이다. 현재의 거부는 모델이 허용하는 것을 UI가 막고 있는 상태다.

### ⚠️ 조건 — 잘림이 드래그 중에 보여야 한다

놓고 나서 "60분만 들어갔네"가 되면 **D13에서 해결한 예측 불가능 문제가 재현된다.**

→ 고스트가 빈 구간에 진입하는 순간 **들어갈 크기(60분)로 줄어들어야** 한다. 이미 고스트가 있으므로 크기 계산만 추가된다.
→ 라벨 예: `60분 · 남은 80분`

### 정한 것

- **최소 크기 제한은 두지 않는다.** 빈 구간이 10분뿐이면 10분이 배치된다. 고스트에 보이므로 사용자가 판단하면 된다. 최소값을 두면 상수와 예외 규칙이 하나 늘어난다.
- **그리드 끝(익일 03:00)에도 같은 규칙을 적용한다.** 마지막 구간에서도 남은 공간만큼만 잘린다.

## D18. 블록 클릭이 탭을 전환하지 않는다

### 문제

타임박스의 블록을 클릭하면 **무조건 "저녁 기록" 탭으로 전환된다.** 그러나 실사용에서는 블록을 선택해 두고 이동·리사이즈를 검토하는 경우가 더 잦다.

### 결정

**블록 선택과 탭 전환을 분리한다. 탭 이동은 탭 버튼을 직접 눌렀을 때만.**

**근거 — 이것은 이전 결정의 잔재다.**
D14에서 **블록 상태 표식 클릭 = 상태 순환**으로 확정했다. 즉 기록은 **표식으로** 하는 것이지 탭 전환으로 하는 것이 아니다. 블록 클릭이 탭을 바꾸는 동작은 그 결정 이전에 만들어진 것으로, 지금은 어긋난다.

블록을 고르는 것은 **"이것을 만지겠다"**는 뜻이지 **"기록하겠다"**가 아니다.

### 소스 확인 필요

- 블록 선택 시 좌측 편집 카드 연동(Task 007)은 유지되는가? **유지되어야 한다** — 탭 전환만 제거하고 선택→편집 카드 연동은 그대로 둔다.

## D19. 계획 총량 초과 시 표시

### 상황

`day3box 작업`의 계획 총량 180분. 빈 구간 60분에 맞춰 2/3 블록을 30분→60분으로 늘렸더니 배치 합계가 **210분**이 되었다. 현재는 TOP3 카드 문구가 `210분 배치됨`으로 바뀔 뿐이다.

### ⚠️ 전제 — 초과는 오류가 아니다

ADR-0002에서 est와 블록을 비동기화한 이유가 이것이다. **est는 아침의 추정이고, 블록은 하루를 보며 내린 판단**이다. 60분 빈칸을 60분으로 채운 것은 정상적이며 오히려 좋은 배치다. 따라서 **경고·차단·자동 보정은 모두 부적절하다.**

### 결정 — 안 3 채택: 두 숫자를 나란히 표시

```
210분 / 계획 180분
```

- 초과분을 **아주 옅게 강조**하되 **경고색(빨강·주황)이나 경고 아이콘을 쓰지 않는다.** 붙이는 순간 "잘못했다"가 되고, 이 제품은 실패를 전시하지 않는다.
- 줄이면 다시 `180분 배치됨`으로 자연히 돌아온다 (계획 총량은 그대로 유지).

**이 표시가 주는 실제 가치**: "내 추정이 30분 짧았다"는 피드백이 된다. 소요시간 추정이 늘 빗나가는 것은 타임박싱의 고질적 문제이며, 이 표시가 그 학습 신호가 된다.

### 배제한 대안

| 안                                         | 배제 사유                                                                                                                                           |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. 현행 (`210분 배치됨`만)**             | 계획이 180이었다는 정보가 사라진다                                                                                                                  |
| **2. "180분 모두 배치. 추가할까요?" 안내** | 정상 상태에 확인을 요구한다. v0에 모달 표면이 0개인데 여기서 만들 이유가 없다                                                                       |
| **4. 마지막 블록을 자동으로 축소**         | **가장 파괴적.** 사용자가 명시적으로 한 배치를 시스템이 조용히 되돌린다. 현재 3/3은 110분인데 자동으로 80분이 되면 그것은 사용자가 정한 값이 아니다 |

### 선택 사항 (여유 있으면)

초과 표시 옆에 **`계획을 210분으로`** 같은 조용한 한 줄. 사용자가 원할 때만 est를 실제에 맞춘다. **자동이 아니라 명시적 행위**이므로 안 4의 문제가 없다. 없어도 무방하다.
