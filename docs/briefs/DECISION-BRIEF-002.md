# Decision Brief #002 — v0 실사용 피드백 반영

> **작성 맥락**: v0 배포 후 실사용 중 발견된 마찰 6건에 대한 논의와 결정.
> **이 문서의 성격**: 확정된 명세가 아니라 **결정 + 근거 + 배제한 대안**의 묶음이다.
> Claude Code에서 실제 소스와 대조해 적합성을 판단한 뒤, 필요 시 조정하고 PRD/ROADMAP에 반영한다.
> **판단 요청**: 각 항목의 "소스 확인 필요" 절을 실제 코드와 대조할 것. 결정이 현재 구현과
> 충돌하거나 더 싼 방법이 있으면 그 근거와 함께 역제안할 것.

## D1. 타임라인 드래그로 블록 직접 생성

### 결정
타임박스 그리드의 빈 영역에서 클릭 후 y축 드래그 → 놓으면 해당 범위에 블록 생성. 구글 캘린더 일별 보기와 동일한 인터랙션.

### 근거
PRD 7장 #4에 이미 예고된 판단 시점이다 — *"배치 방식: 클릭 → 다음 빈 슬롯 자동 배치. drag-across는 실사용 후 판단"*. 실사용에서 마찰이 확인되었으므로 예정대로 도입한다.

현재는 좌측(brain dump / TOP3)에서만 항목을 만들 수 있어, 타임라인에서 일정을 조정하다가 새 항목이 필요하면 좌측으로 이동해야 하는 왕복이 발생한다.

### 제약 (반드시 준수)
- **10분 스냅** 적용 (D5와 일관)
- **겹침 금지** 규칙 적용 (PRD 4.1)
- 생성되는 항목은 TOP3가 아니라 **고정 시간(`kind='fixed'`)** — D2 참조

### 소스 확인 필요
- 기존 블록 이동/리사이즈(F5)의 pointer 핸들링과 로직을 공유할 수 있는가? 드래그-생성은 "빈 영역에서 시작하는 리사이즈"와 사실상 같은 계산이다. 중복 구현을 피할 것.
- 겹침 검사 함수가 이미 있다면 재사용. 없다면 생성/이동/리사이즈가 같은 함수를 쓰도록 정리.

## D2. `tasks.kind` — 할 일과 고정 시간의 구분

### 배경: 이전 판단을 뒤집었다
초안에서는 "드래그로 생성된 항목도 brain dump에 표시한다"고 판단했다. 근거는 데이터 모델상 task 행이 반드시 생기므로 숨은 상태를 만들지 말자는 것이었다.

**이 판단은 전제가 틀렸다.** 드래그로 만들 항목이 무엇인지 확인해보니 샤워·식사·이동·휴식·개인 약속(장보기, 티타임, 지인 식사)이었다. 이것은 **할 일이 아니라 시간을 확보하는 것**이다.

방법론이 이를 뒷받침한다. 원본 타임박싱 절차 5단계는 *"우선순위가 낮은 할 일을 끼워넣거나 **휴식 시간을 확보한다**"* 이다. 확보(secure)와 할 일(todo)은 원래부터 구분된 행위다. brain dump에 "밥먹기"가 섞이면 좌측의 의미("머릿속을 다 비운다")가 희석된다.

### 결정: 스키마
```sql
alter table public.tasks
  add column kind text not null default 'task'
  check (kind in ('task','fixed'));
```

- `'task'` — brain dump 항목. 좌측에 표시. TOP3 승격 가능.
- `'fixed'` — 고정 시간. 좌측에 **미표시**. 타임박스에만 존재. TOP3 승격 불가.

brain dump 조회에 `kind = 'task'` 필터 추가.

### 배제한 대안: `blocks.task_id`를 nullable로
블록이 task 없이 존재할 수 있게 하고 제목을 block에 직접 두는 방식. **배제 사유**: 제목이 tasks와 blocks 양쪽에 존재하게 되어 PRD 4.1의 정규화 결정이 깨진다. 모든 블록 조회가 left join + null 분기가 되어 코드가 지저분해진다. 컬럼 하나 추가가 훨씬 싸다.

### 경계선 (오버엔지니어링 방어)
**`kind`는 두 값짜리 구분이지 카테고리 시스템이 아니다.** 값이 3개 이상으로 늘어나거나, kind 관리 UI가 생기거나, kind별 설정이 붙기 시작하면 그것은 범위 이탈이다.

### 소스 확인 필요
- brain dump 조회 쿼리 위치 — `kind='task'` 필터 누락 시 고정 시간이 좌측에 새어 나온다.
- TOP3 승격 로직 — `kind='fixed'`는 승격 대상에서 제외되어야 한다.
- "어제에서 이월" 기능 — 고정 시간은 이월 대상이 아니다(밥먹기를 내일로 이월하지 않는다). 이월 쿼리에도 필터 필요.
- 기존 데이터는 전부 `'task'`로 채워지므로 마이그레이션 부담 없음 (default 존재).

## D3. 고정 시간 블록의 시각 처리

### 후보 두 가지

**안 A — 빗금(hatching)**
의미상 정확하다. 캘린더 UI에서 hatching은 관례적으로 "점유됐지만 작업은 아님"을 뜻한다.
**비용**: v1에서 그리드를 이미지로 뽑아 공유하는데, 빗금 블록이 여러 개면 이미지가 어수선해진다. 또한 v1에서 블록 안에 사진이 들어가면 빗금과 시각적으로 충돌한다.

**안 B — 좌측 막대 제거 (권장)**
현재 화면에 이미 위계가 존재한다. 그 어휘의 마지막 단계를 쓴다.

| 종류 | 좌측 세로 막대 | 본문 |
|---|---|---|
| TOP3 | 컬러 | 회색 |
| 일반 task | 회색 | 회색 |
| **고정 시간** | **없음** | **더 옅게 / 외곽선만** |

새 시각 요소를 도입하지 않고, 막대의 부재가 "이건 일이 아니다"를 즉각 전달한다. 이미지로 뽑아도 조용하다.

### 결정
**안 B를 우선 구현하되, 둘 다 만들어 실제 화면에서 비교한다.** CSS 수준이라 되돌리기가 싸다.
**판단 기준**: 블록이 3~4개인 날이 아니라 **하루가 꽉 찬 날**에 깔끔한가. 항목이 적을 때는 어떤 안이든 괜찮아 보인다.

## D4. 긴 TOP3 작업의 블록 분할

### 조사 결과가 전제를 뒤집었다
"180분 블록이 하나로만 세팅되어 불편하다"는 문제 제기였으나, 타임박싱 방법론을 재확인한 결과:

- 널리 알려진 "5분 단위"는 **머스크 본인이 엄격히 따른다는 것을 부인**했으며, 오히려 생각하고 창의적이 되려면 **긴 방해받지 않는 시간**이 필요하다고 언급했다. 5분이라는 구체적 단위는 과장되었거나 예전 방식일 수 있다.
- 5분 단위의 취지는 정밀한 계측이 아니라 **"지금 이 시간은 무엇을 위한 시간인가"를 계속 묻게 만드는 장치**에 가깝다.

따라서 **180분 단일 블록은 문제가 아니라 정상이다.** TOP3는 깊은 집중이 필요한 일이고, 그런 일에는 긴 연속 시간이 맞다. 60분×3으로 쪼개는 것은 방법론에 어긋난다.

### 진짜 문제는 다른 것이었다
실제 서술은 *"중간에 점심 시간이나 어떤 일정이 있을 경우 중간을 띄우고 싶은데"* 였다.
이것은 **작업을 분해하고 싶은 것이 아니라, 중간에 장애물이 있는 것**이다. 작업 분해 문제가 아니라 **배치 문제**다.

### 결정: 블록 분할 (1 task : N blocks)
같은 task가 두 개 이상의 블록으로 배치될 수 있게 한다. 예: `day3box 작업` → 12:30–14:00 + 15:00–16:30.

**이것은 스키마가 이미 지원한다.** PRD 4장에서 `tasks` 1:N `blocks`로 설계했고, *"하나의 task가 여러 블록으로 쪼개질 수 있다(2시간을 오전·오후로 분할)"* 는 예시까지 명시했다. 모델은 열려 있고 UI만 v0에서 제외했던 것이므로, **추가 스키마 변경이 없다.**

### 구현 시 준수
- 분할된 블록들은 **같은 `task_id`를 참조**한다. 같은 제목·같은 색으로 렌더링되어야 "하나의 일인데 시간이 나뉜 것"이라는 의미가 유지된다.
- `est_min`은 task에 **하나로 유지**한다. 블록들의 길이 합이 이를 채우는 구조.
- 화면에 `(1/2)` 같은 표시는 선택 사항. 데이터상으로는 동일 task다.

### 배제한 대안

**대안 2 — 작업1/작업2/작업3으로 나눠 등록**: TOP3 슬롯 3개를 한 작업이 전부 소비한다. 자명하게 부적합.

**대안 3 — TOP3의 하위 task 계층**: **명확히 반대한다.** TOP3 3개에 각각 하위 3개를 달면 실질 항목이 9개가 되고, 그것은 다시 todo 리스트다. PRD 1.4의 "우선순위 강제"라는 제품 정체성과 7.1의 하드 제한이 정확히 이것을 막기 위한 장치였다. 또한 5분 단위의 취지가 "우선순위를 계속 묻게 만드는 것"이라면, 하위 작업으로 잘게 쪼개는 것은 **묻기를 회피하는 방향**이다.

### 소스 확인 필요
- **블록 조회/렌더링 코드가 "task당 블록 1개"를 암묵적으로 가정하고 있는가?** 스키마는 1:N이지만 구현이 1:1을 전제로 작성됐을 가능성이 높다(예: `find` 사용, task별 단일 블록 매핑). 이 부분이 이번 변경의 주 작업량이 될 것.
- TOP3 패널에서 "배치됨/미배치" 상태 판정 로직 — 블록이 여러 개일 때 어떻게 판단하는가.
- `est_min`과 블록 길이 합의 관계를 UI에 어떻게 표시할지 (예: "180분 중 120분 배치됨").

## D5. 스냅 단위 15분 → 10분

### 근본 원인 (스크린샷에서 확인됨)
`등+이두 80분 → 16:00–17:20`. **17:20은 15분 격자 위가 아니다.**

즉 **시작점은 15분에 스냅되지만 블록 길이는 `est_min` 자유값**이다. 두 단위가 다르므로 끝점이 격자를 벗어나고, 다음 블록이 맞물리지 않는다.

**스냅만 잘게 쪼개는 것은 해결이 아니다.** 80분은 5·10분으로 나뉘지만, 25분이나 100분을 입력하면 다시 어긋난다. 두 가지를 함께 고쳐야 한다.

### 결정
1. **스냅 단위 10분**
2. **`est_min`도 10분 배수로 제약** (D6)

두 단위를 일치시켜야 끝점이 항상 격자 위에 온다. 이것이 실제 해결책이다.

### 왜 5분이 아닌가
- 06:00–24:00 구간이 216칸이 된다. 1시간이 60px이면 한 칸이 5px.
- 드래그 정밀도가 떨어지고, **v1 모바일에서 손가락으로 잡기 어렵다**.
- 10분은 60의 약수라 시간 경계에 깔끔히 떨어지고, 20/30/40/50/80/90/120 등 자연스러운 소요시간을 모두 커버한다.
- 방법론상으로도 5분 고수는 근거가 약하다(D4 조사 결과 참조).

### 소스 확인 필요
- **스냅 값이 상수로 분리되어 있는가, 하드코딩되어 있는가.** 여러 곳(생성/이동/리사이즈)에 15가 흩어져 있으면 상수로 통합할 것.
- 그리드 렌더링의 눈금 간격도 함께 조정 필요 여부.

## D6. 소요시간 입력 — 자유 입력 제거

### 문제: 185분, 53분은 정밀한 것이 아니라 **가짜 정밀**이다
아무도 자기 작업이 53분 걸린다는 것을 모른다. 50분인지 60분인지도 모른다. 그런데 자유 숫자 입력창은 사용자로 하여금 **정확해야 한다고 착각**하게 만들고, 존재하지 않는 정밀도를 생성한다. 그 값이 격자를 깨뜨려 D5의 문제를 만든다.

방법론상으로도 4단계는 *"소요 시간을 함께 작성한다"* 이지 *"정확히 측정한다"* 가 아니다. **어림 판단**이다. 5분 단위의 취지가 계측이 아니라 질문을 유도하는 장치라면, 1분 단위 입력은 그 질문에 기여하지 않고 오히려 방해한다.

**따라서 입력 제한은 기능 축소가 아니라 교정이다.** 자유도를 넓히는 방향은 반대한다.

### 결정: 칩(주) + 스테퍼(보조), 자유 입력 제거
```
[30분] [60분] [90분] [120분] [180분]     ‹ ▾ 60분 ▴ ›
```

- **칩(chip)이 주**: 대부분 한 번의 탭으로 끝난다. 프리셋 자체가 "이건 어림값"이라는 메시지를 전달한다. v1 모바일에서도 탭 타깃으로 유리하다.
- **스테퍼(stepper / spin button)는 ±10분 보조**: 90과 120 사이가 필요할 때만. 스테퍼 단독은 불가(0→180까지 18번 눌러야 함).
- **자유 텍스트 입력은 제거한다.** 남겨두면 53분이 다시 들어온다.

프리셋 값을 길게 잡은 이유: TOP3는 깊은 집중 작업이며, 조사 결과 긴 연속 시간이 방법론에 부합한다. 15분·20분 같은 짧은 프리셋은 TOP3 성격에 맞지 않는다.

### 배제한 대안
- **휠 피커(wheel picker)**: 데스크톱에서 어색. 구현 비용 대비 이득 없음.
- **슬라이더**: 정밀도가 나쁘고 값 확인이 어렵다.

### 핵심 인사이트: 정밀 조정은 이미 존재한다
그리드에서 블록 가장자리를 끌면 길이가 바뀐다(F5). 거기서 10분 단위로 조정된다. 역할 분담은 이렇다:

| 위치 | 역할 |
|---|---|
| 좌측 칩/스테퍼 | **어림값 설정** — 블록 배치를 위한 시작점 |
| 우측 블록 리사이즈 | **실제 조정** — 다른 블록과 맞물리게 |

좌측에 정밀 입력을 두는 것은 **기능 중복**이다.

### 기존 데이터 마이그레이션
```sql
-- 10분 배수로 반올림 (185 → 190, 53 → 50)
update public.tasks
set est_min = round(est_min / 10.0) * 10
where est_min is not null and est_min % 10 <> 0;

-- 이후 제약
alter table public.tasks
  add constraint tasks_est_min_step
  check (est_min is null or est_min % 10 = 0);
```
UI가 뚫려도 DB가 막는다. 기존 `end_min > start_min` 제약과 같은 성격.

### 소스 확인 필요
- `est_min` 입력 컴포넌트 위치. 자유 입력이 여러 곳에 있는지.
- 블록 리사이즈가 `est_min`을 역으로 갱신하는가? (블록을 늘리면 task의 est_min도 바뀌는가) — D4의 분할과 함께 정의가 필요한 지점. **분할이 도입되면 "블록 길이 합 ≠ est_min"인 상태가 정상적으로 존재할 수 있으므로**, 리사이즈가 est_min을 자동 갱신하면 안 될 가능성이 높다. 이 부분은 소스를 보고 판단할 것.

## 8. Claude Code 판단 요청 사항

1. **각 D 항목이 현재 소스와 충돌하는가?** 특히 D4(1:N 렌더링 가정)와 D5(스냅 상수 분산).
2. **더 싼 구현 경로가 있는가?** 특히 D1(드래그 생성)이 기존 F5 리사이즈 로직과 얼마나 공유 가능한지.
3. **D6의 `est_min` ↔ 블록 길이 관계**를 현재 코드가 어떻게 다루는지 확인 후, 분할 도입 시의 정합성 규칙을 제안할 것.
4. **작업 순서 제안.** 참고: 논의 시점의 우선순위는 **D4/D5/D6 먼저, D1/D2/D3 나중**이었다. 근거는 "매일 쓰는 데 무엇이 더 막히는가" — 점심시간이 낀 180분 블록은 매일 발생하며 우회로가 없다. D1은 불편하지만 우회로가 있다(좌측에서 추가 → 배치). 다만 D5/D6은 D1의 전제이기도 하므로 실제 의존 관계를 보고 조정할 것.
5. **범위 이탈 감시.** 이 브리프의 결정을 구현하다가 새 추상화 계층, 새 테이블, 설정 UI 등이 필요해 보이면 **멈추고 먼저 보고할 것.** 이 프로젝트의 최대 리스크는 오버엔지니어링이다.
