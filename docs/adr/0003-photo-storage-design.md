# ADR-0003: 사진 저장·압축 설계 (R3 실험 기반)

- **상태**: 제안 (2026-08-04 — 오너 검증 대기, Task 018 구현 완료 시 채택으로 승격)
- **관련**: Phase 9 / Task 018, DECISION-BRIEF-006 §6, ROADMAP_v1 v1절 "R3 검증 설계", Lean Canvas ⑦(Storage = 유일한 비선형 비용)·R3

## 맥락

v1 첫 단계 R3(사진 입력 마찰 검증)를 위해 사진 저장이 처음 도입된다. 정본에 확정돼 있는 제약: **원본 해상도 저장 금지**, Storage는 유일한 비선형 비용이라 **압축·리사이즈 정책을 착수 시 반드시 함께 결정**, 데이터 모델은 "미래 테이블을 미리 만들지 않는다", 실패를 전시하지 않는다(사진 원본 URL이 밖으로 돌아다니면 안 된다).

이 결정 묶음은 하나의 비가역성을 공유한다 — **원본은 폐기되고, 경로 규칙 위에 데이터가 축적된다.** 나중에 바꾸려면 저장된 사진 전체의 마이그레이션이 필요하므로 한 문서로 함께 기록한다.

## 결정

| 항목 | 결정 |
|---|---|
| 버킷 | `photos`, **private** |
| 경로 규칙 | `{user_id}/{date}/{block_id}.webp` |
| 데이터 모델 | `blocks.photo_path text null` + `blocks.photo_added_at timestamptz null` — **한 블록 = 1장**, 새 테이블 없음 |
| 업로드 경로 | **브라우저 → Storage 직접 업로드**(upsert) → 성공 후 서버 액션이 경로 검증·기록 |
| 압축 | **클라이언트** canvas 리사이즈 — 긴 변 **1600px**, **WebP 품질 0.8** (미지원 시 JPEG 0.82), 장당 예상 150~400KB |
| 조회 | `createSignedUrl` (1시간) |
| 접근 제어 | storage RLS `(storage.foldername(name))[1] = auth.uid()::text` (select·insert·update·delete) + 서버 액션의 경로 프리픽스 검증 이중 방어 |

### 각 결정의 왜

- **private 버킷**: 공유는 뒤 단계의 "내보낸 이미지"로 하는 것이지 원본 사진 URL로 하는 게 아니다. public은 유출 시 되돌릴 수 없다(경로가 퍼진다).
- **경로 규칙**: 1세그먼트 `user_id`는 storage RLS 표준 패턴과 정합. 파일명이 `block_id`라 교체가 자연 덮어쓰기(upsert)가 되어 고아 파일이 최소화된다(청소 배치 불필요). `date` 폴더는 집계·디버깅용.
- **blocks 1:1 컬럼**: R3 가설은 "블록 자리에 사진"이지 갤러리가 아니다. 기존 `blocks` RLS(`user_id = auth.uid()`)가 그대로 커버해 정책 추가가 없다. `photo_added_at`은 보조 지표(당일 즉시 vs 저녁 몰아넣기 판별)용.
- **직접 업로드**: 서버 액션 경유는 Vercel body 제한(~4.5MB)에 걸리고 전송이 2배다. 소유는 storage RLS가 보장하고, **업로드 성공 후에만 컬럼을 기록**하므로 트랜잭션 없이도 정합(실패 시 남는 파일은 덮어쓰기 경로가 흡수). 삭제는 보상 패턴 — storage remove 시도 후 성공 여부와 무관하게 컬럼 null 우선.
- **1600px / WebP 0.8**: 미래 최대 소비처(하루 그리드 이미지·콜라주)에서 사진 한 장의 실표시 폭은 수백 px — 2x 레티나 감안 1600px이면 어떤 표현안에도 충분하고 원본(4000px+) 대비 용량 약 1/10. Supabase Free 1GB 기준 300KB × 5장/일 × 365일 ≈ 550MB/년/인 — 실험 규모에서 비선형 비용이 선형화된다. 구현은 `createImageBitmap(file, {imageOrientation:'from-image'})`(EXIF 회전) → canvas → `toBlob`, 유틸 1개(~30줄). 실기기는 iPhone iOS 17+(Safari WebP 저장 지원)로 확인됨 — JPEG fallback은 코드로만 유지.

## 배제한 대안

- **public 버킷 + 공개 URL**: 유출 비가역. "실패를 전시하지 않는다" 원칙과도 충돌(원본이 문맥 없이 돌아다님).
- **`block_photos` 1:N 테이블**: 콜라주·다중 장은 표현 단계의 가설이다. 그 시점의 테이블 신설·이관 비용은 사진 수십 장 규모에서 사소하다. "미래 테이블을 미리 만들지 않는다" 관례 준수.
- **서버 액션 경유 업로드**: body 제한·전송 2배·FormData 파일 전송 선례 없음(현 코드 관례는 typed 인자).
- **이미지 압축 라이브러리**(browser-image-compression 등): canvas로 충분 — 의존성 규율.
- **서버/Edge Function 리사이즈**(sharp): 비용 지점(Storage·전송)보다 앞(클라이언트)에서 잘라야 하고, 함수 유지 비용이 추가된다.
- **원본 병행 저장**: 정본에서 금지 확정 (ROADMAP_v1 v1절).

## 결과

**긍정**: 정책 추가 없이 기존 RLS 체계에 편입. 교체·삭제가 단순(덮어쓰기·보상 패턴). 저장 용량이 실험 규모에서 예측 가능.

**비용**: 원본 폐기 — 표현 단계에서 1600px 이상이 필요해지면 재촬영 외 방법이 없다(콜라주·내보내기의 실표시 크기상 발생 가능성 낮다고 판단). 1:N 요구가 오면 테이블 신설 + 컬럼 이관 마이그레이션 1회.

**주의**: 서명 URL(1시간)이라 이미지 주소를 캐시·공유할 수 없다 — 표현 단계의 "이미지 다운로드"는 원본 URL이 아니라 렌더링 산출물로 해결해야 한다(이 제약은 의도된 것). ADR-0001 미러 규칙에 따라 사진 상태도 낙관 reducer(`setPhoto`/`removePhoto`)와 서버 액션이 일치해야 한다.

- **서명 URL 만료(1시간)와 R3 검증의 간섭**: 탭을 오래 열어두면 이미지가 깨져 보인다.
  실기기 테스트(Task 018)에서 만료 후 동작을 확인하고, 필요하면 만료 시 재발급 또는
  검증 기간 한정 유효기간 연장을 적용한다. **이 현상이 마찰 원인 ③으로 잘못 기록되면
  R3 판정이 오염된다.**
